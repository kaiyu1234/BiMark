# BiMark 多 bit 水印方案与代码深度分析

## 1. 方案概述（基于当前实现反推）

当前仓库实现的是一个**基于随机词表划分（random partition）与前缀伪随机控制（prefix-conditioned PRF）**的多 bit 水印方案。

其核心思路可以概括为：

1. 先用若干个 `partition_seeds` 把词表固定划分成多个 50/50 的子集；每个 seed 对应一个二值划分。
2. 每个生成位置读取最近 `window_size` 个 token 作为前缀，用 `prf(prefix, key)` 派生：
   - `c_seed`：决定当前位置是否对某个 partition 做“翻转”；
   - `bit_idx_seed`：决定当前位置承载消息中的哪一位 `bit_idx`。
3. 对于被选中的 bit，如果目标 bit 与 `c` 的异或关系满足某种条件，就提高该 partition 内 token 的概率；否则提高 partition 外 token 的概率。
4. 检测时重新计算相同前缀的 PRF、partition 与 `bit_idx`，统计每一位 bit 在各位置上的“支持票数”，最后用多数投票和 z-test 做检测与解码。

本质上，它是把**零 bit 绿表水印**推广成了**多个并行二元判别器**：

- 每个 partition 类似一个弱分类器；
- 每个位置只给消息中的某一位 bit 投票；
- 多个 partition 在同一位置对同一位 bit 重复投票；
- 最后再对各 bit 聚合统计量并恢复消息。

## 2. 当前代码里真正发生了什么

### 2.1 生成端（嵌入）

`WatermarkBimark.py` 的 `WatermarkBimark` 在初始化时一次性生成多个固定 partition mask。随后在每个生成步：

- 只操作 `top_k` token 的概率，而不是完整词表；
- 用前缀计算 `c_seed` 和 `bit_idx_seed`；
- 随机选择一个消息位 `bit_idx`；
- 对每个 partition 依据 `(c, bit)` 的关系，决定该 partition 内概率乘 `(1+delta)` 还是 partition 外概率乘 `(1-beta)`；
- 若当前前缀已经出现过，则跳过该位置，不嵌入水印。

这意味着该实现实际上采用的是：

- **固定 partition，动态 bit 选择**；
- **局部 top-k 重加权**；
- **基于重复前缀跳过的去重嵌入**；
- **每个位置只服务一个 bit** 的时分复用设计。

### 2.2 检测端（解码）

`detect_watermark_dump.py` 中 `decode_bimark_multibit_watermark` 和 `verify_bimark_multibit` 会：

- 重建相同的 partition；
- 用相同 PRF 从前缀恢复 `c` 与 `bit_idx`；
- 对每个位置、每个 partition 统计当前 token 对 0/1 哪一侧更支持；
- 对每位 bit 单独累计票数；
- 输出整段文本的 z-score、每位 bit 的 z-score、逐长度 stride 的解码结果。

因此它把消息恢复问题简化成：

- **每位 bit 的独立二分类**；
- **总体水印存在性的单侧 z-test**；
- **逐长度切片观察解码随文本长度增长的收敛行为**。

## 3. 这个方案的优点

从研究原型角度，这套设计有几个明显优点：

1. **实现简单**：生成与检测都只依赖 PRF 和固定随机 partition，不需要训练额外模型。
2. **密钥化自然**：`partition_seeds`、`c_key`、`bit_idx_key` 构成天然密钥空间。
3. **多 bit 可扩展**：通过 `bit_idx` 选择消息位，原则上可以扩展消息长度。
4. **检测端可解释**：每位 bit 的票数、z-score、hit-rate 都能直观看到。
5. **与采样式生成兼容**：嵌入通过 logits processor 实现，接入 HuggingFace 生成流程很直接。

但这些优点主要停留在“可运行原型”层面。一旦想做成高质量论文，特别是要强调**短文本中的多 bit 嵌入**，当前方案会遇到比较系统性的瓶颈。

## 4. 当前方案的核心痛点

### 4.1 最大痛点：短文本里“每个位置只承载 1 位 bit”导致容量极低

当前实现每个 token 位置只通过 `bit_idx_seed` 选中**一个 bit**。如果消息长度为 `m`、有效可嵌入位置数为 `T`，那么每位 bit 平均只拿到大约 `T / m` 次投票。

这在长文本里还能靠样本数弥补，但在短文本里会出现三个问题：

1. **每位 bit 采样数严重不足**；
2. **不同 bit 的命中次数方差大**，有的 bit 几乎没被覆盖；
3. **检测统计量极不稳定**，出现很多 `x`（平票或低置信度）。

这其实是当前方案最限制论文创新空间的地方：

> 它不是“短文本难”，而是“设计上把短文本本就稀缺的位置预算又切碎了”。

### 4.2 固定均匀随机 `bit_idx` 分配，没有做覆盖率控制

当前 `bit_idx` 由 PRF 直接均匀采样。理论上无偏，但短文本下不合理：

- 某些 bit 可能被分到很多次；
- 某些 bit 可能一次都没轮到；
- 不同样本间消息位可靠性差异很大。

也就是说，当前方案没有显式解决**bit coverage**问题。对于短文本，多 bit 恢复的首要目标不是“均匀随机”，而是“尽量让每位 bit 至少被写到几次”。

### 4.3 partition 固定为 50/50 随机划分，但没有利用 token 概率结构

当前每个 partition 都是对整个词表随机二分，然后只在 `top_k` 上生效。这里有两个效率损失：

1. **随机划分与模型当前分布不匹配**：高概率 token 可能恰好集中到一边，使该步可控性差。
2. **不同 partition 信息增益高度冗余**：多个随机 mask 不一定提供真正独立的证据。

对于短文本，每一个可嵌入位置都很珍贵，所以 partition 设计应该追求**每步最大 Fisher information / KL 增益**，而不是简单随机。

### 4.4 `top_k` 截断会额外损失嵌入信号

嵌入只在 `top_k` 上改权，这会带来两个副作用：

- 原始分布尾部质量被直接丢弃；
- 如果某步模型本来有效候选非常少，`top_k` 改权空间其实有限。

更关键的是，检测端假设的统计结构与生成端真实生效的分布不完全一致，因为检测端只根据最终 token 落在哪个 partition 统计，而不知道该步 top-k 截断后到底有多少有效偏置空间。

短文本下，任何一次嵌入强度不足都会直接伤害 bit 恢复率，所以 `top_k` 的粗糙截断并不理想。

### 4.5 `delta/beta` 调制比较粗糙，没有做熵感知与语义风险控制

当前 `delta` 由 `alpha/p0` 与 `1+prob_delta` 做裁剪得到，本质上是个较简单的概率缩放。问题在于：

- 没有区分高熵位置和低熵位置；
- 没有区分语义敏感 token 与普通功能词；
- 没有区分“当前步是否值得嵌入”。

短文本尤其怕语义质量下降：因为 token 数少，每个 token 对语义和可读性的边际影响更大。如果还沿用统一强度，往往会陷入两难：

- `delta` 小：检测不到；
- `delta` 大：文本质量明显下降。

### 4.6 跳过重复前缀虽然能减少相关性，但短文本下会进一步减少可用位置

当前实现会对重复前缀直接跳过。对于长文本这是合理的防相关设计，但在短文本里：

- 本来 token 数就少；
- 常见短句/模板句中重复上下文很多；
- 一跳过就进一步压缩有效样本量。

所以它对短文本多 bit 很不友好。

### 4.7 检测器仍是“硬投票 + z-test”，没有充分利用软信息

当前检测基本是：

- token 落在哪一边，就给 0/1 累加 1 票；
- 最后多数投票 + z-score。

但生成端其实有更多可利用信息：

- 每个位置的原始概率分布；
- token 距离决策边界有多远；
- 多个 partition 的置信度是否一致；
- 某些位置是否处于高熵/低熵状态。

用硬投票会损失大量统计效率。短文本下，本来就只有很少样本，更应该做**软判决（soft decoding）**。

### 4.8 没有任何纠错编码（ECC）或不等保护机制

当前多 bit 消息基本是裸嵌入。这样一来：

- 任意几个 bit 解错就整条消息错；
- 没有考虑不同 bit 的置信度差异；
- 没有“重要位”和“非重要位”之分。

短文本里裸嵌入几乎天然吃亏，因为每位 bit 的样本数太少。论文层面如果想把短文本多 bit 做出来，ECC 基本是必备组件，而不是可选项。

### 4.9 鲁棒性攻击面仍较脆弱：释义、删改、截断、局部编辑

当前代码虽然提供 DIPPER paraphrase 测试接口，但方案本身没有专门为**编辑鲁棒性**设计同步机制：

- 一旦删掉前面几个 token，后续前缀全部变了；
- paraphrase 会改变词面 token，导致后续 PRF 链条整体漂移；
- 短文本尤其经不起这种“前缀错位”。

换句话说，当前方案本质上更像**精确 token 级同步水印**，而不是**编辑鲁棒水印**。

### 4.10 实现层面的若干代码问题，会影响论文实验可信度

如果要以此为基础写论文，代码本身也有一些需要先修正/解释的问题：

1. `detect_watermark_dump.py` 中 `decode_bimark_multibit_watermark` 被定义了两次，前一个版本实际上被后一个覆盖，容易造成实验歧义。
2. `verify_bimark_multibit` 中 `weight = [1 for _ in range(partition_seeds)]` 明显应为 `len(partition_seeds)`，否则语义不一致。
3. 生成端使用固定 partition，检测端也是固定 partition；但文件里还保留了“按前缀动态生成 partition”的旧版本接口，说明实验设计可能经历过变化，需明确最终方案。
4. `WatermarkBimark.__call__` 中 `if prefix[i] in self.hist[i]` / `self.hist[i].add(prefix[i])` 直接把 Tensor 当作 set 元素，这种写法依赖 Python/Torch 的对象行为，不够稳健，跨设备/跨版本可复现性值得检查。
5. 生成时打印每步 `time cost` 会极大污染性能测试。
6. `auth_token = "xxx"`、硬编码 `CUDA_VISIBLE_DEVICES=0` 等不利于复现实验。

这些问题本身不是理论缺陷，但会影响论文审稿人对实现可靠性的判断。

## 5. 为什么“短文本多 bit”特别难

要想把论文重点放在短文本，需要先讲清楚困难来自哪里。可概括为四个矛盾：

### 5.1 容量与可靠性矛盾

短文本 token 少，想塞更多 bit，就必须让每位 bit 使用更少的位置，导致误码率上升。

### 5.2 可靠性与文本质量矛盾

为了弥补位置少，就要加大偏置强度；但偏置强了，文本自然度、困惑度和语义保真会变差。

### 5.3 同步与鲁棒性矛盾

短文本没有冗余，一旦 token 被删改，后续位置全部错位；但为了对抗编辑，又需要同步标记或冗余，会进一步占掉容量。

### 5.4 检测显著性与多 bit 解码矛盾

零 bit 检测只要证明“有水印”即可；多 bit 还要逐位恢复消息。短文本里统计量刚够做存在性检测时，往往还远远不够做可靠解码。

所以如果新论文想要真正有说服力，不能只是在当前框架里微调 `delta` 或增大 partition 数；必须从**位置分配、软判决、纠错、同步鲁棒性**几个层面同时改。

## 6. 我建议的新论文方向：面向短文本的自适应多 bit 水印

下面给出一个相对完整、可写成论文的改进路线。可以把新方法暂定名为：

> **SABER-WM**: Short-text Adaptive Balanced Error-corrected Robust Watermarking

或者中文名：

> **面向短文本的自适应平衡纠错多 bit 水印**

### 6.1 核心思想一：从“随机选 bit”改成“覆盖率约束的 bit 调度”

这是最关键的改进。

#### 当前问题

当前每步随机选一个 bit，导致短文本里很多 bit 根本拿不到足够票数。

#### 改进方案

把 `bit_idx` 的选择从“纯随机”改成“伪随机 + 覆盖率平衡调度”：

- 维护每个 bit 当前已分配次数 `n_j`；
- 每个位置优先分配给当前覆盖最少的 bit；
- 再用 PRF 打破平局，保证密钥随机性；
- 可以加入权重，优先保护高重要度 bit（例如 ECC 中的校验位或同步位）。

一种简单实现：

\[
bit\_idx_t = \arg\min_j \; n_j - \lambda \cdot r_{t,j}
\]

其中 `r_{t,j}` 是由 PRF 产生的伪随机扰动，`lambda` 控制随机性与平衡性的折中。

#### 预期收益

- 明显提高每位 bit 的最小覆盖次数；
- 降低 bit 间方差；
- 对短文本尤其有效，因为有限位置被更均衡地利用。

这是我认为最值得做、且最容易形成论文贡献的一点。

### 6.2 核心思想二：从“每位置只写 1 位”改成“分层叠加写入”

#### 当前问题

每个位置只服务一个 bit，导致容量利用率低。

#### 改进方案 A：主位 + 辅位双层嵌入

每个位置不只选择一个 `bit_idx`，而是：

- 主位 bit：用较强偏置；
- 辅位 bit：用较弱偏置；
- 两者使用不同 partition 组或不同强度层。

例如：

- 前 `d1` 个 partition 用于主位；
- 后 `d2` 个 partition 用于辅位；
- 检测时联合 LLR 解码。

这样短文本中每个位置就能贡献不止 1 bit 的信息，而不是完全时分复用。

#### 改进方案 B：码字级嵌入而非裸 bit 嵌入

不是让一个位置对应单个位，而是让它对应一个小码本中的一个符号，例如：

- 每个位置承载 2-bit symbol（00/01/10/11）；
- 用多 partition 模式来区分 4 类而不是 2 类；
- 检测时做多类判别。

这相当于从二元假设升级为多元假设，若设计得好，短文本总容量会更高。

### 6.3 核心思想三：加入软信息检测与 LLR 解码

#### 当前问题

当前检测基本是硬投票。

#### 改进方案

对每个位置、每个 bit，计算对 `bit=1` 相比 `bit=0` 的**对数似然比（LLR）**：

\[
\mathrm{LLR}_{t,j} = \log \frac{P(x_t \mid b_j=1, prefix_t)}{P(x_t \mid b_j=0, prefix_t)}
\]

如果不想完全重跑模型，也可以用近似版本：

- 根据 token 落在各 partition 的情况构造 pseudo-LLR；
- 按 partition 在该步的可分性（如 `|p0-0.5|`、熵、margin）加权；
- 再把同一 bit 的多个位置 LLR 求和。

最后不是做多数投票，而是：

\[
\hat b_j = \mathbb{1}\left[\sum_t \mathrm{LLR}_{t,j} > 0\right]
\]

#### 预期收益

- 短文本下显著提高统计效率；
- 可以自然接入 ECC 的软输入译码；
- 更适合论文中做理论分析（误码率界、Chernoff bound、SPRT 等）。

### 6.4 核心思想四：把 ECC 从“附加模块”升级成“方案主体”

#### 当前问题

裸 bit 嵌入在短文本里误码非常敏感。

#### 改进方案

建议采用**短码长、软输入友好**的 ECC，例如：

- BCH / Reed-Solomon：实现简单，适合先做 baseline；
- Polar / LDPC：更适合配合软信息译码；
- Rateless / Fountain 风格：适合文本长度不固定场景。

具体建议：

1. 原始消息先编码成长度 `m' > m` 的码字；
2. 不同码位按重要性分层：
   - 同步位 / 头部位重点保护；
   - 内容位次级保护；
3. 检测时用每位 LLR 送入软译码器。

#### 为什么这点适合写论文

因为短文本多 bit 的难题，本质上就是“极短块长通信”。把水印看成一个受宿主分布约束的通信信道，ECC 是非常自然、而且理论上说得通的主线。

### 6.5 核心思想五：做熵感知的自适应嵌入强度

#### 当前问题

当前 `delta` 比较统一，没有区分位置价值。

#### 改进方案

在每个位置根据模型分布特征计算一个嵌入预算：

- 高熵位置：可承受更强偏置，容量高；
- 低熵位置：弱嵌入或跳过，避免破坏质量；
- 功能词/标点位置：可考虑低权或禁写；
- 命名实体、数字、代码片段：禁写或极弱写入。

可以定义：

\[
\delta_t = \delta_{max} \cdot g(H_t, margin_t, risk_t)
\]

其中：

- `H_t`：下一词分布熵；
- `margin_t`：top-1 与 top-2 的差距；
- `risk_t`：语义风险分数。

#### 预期收益

- 在相同文本质量约束下提高有效嵌入强度；
- 减少“无效位置”对短文本预算的浪费。

### 6.6 核心思想六：把随机 partition 升级为“信息量最大化 partition”

#### 当前问题

随机二分词表过于粗糙。

#### 改进方案

让 partition 不再只是随机，而是与当前步分布相关：

- 目标是让两边概率尽量接近 0.5，以最大化可分性；
- 同时约束两边 token 的语义风险相近，避免质量劣化；
- 多个 partition 之间尽量低相关，提高独立信息量。

可以做两种版本：

1. **轻量在线版**：仅在 top-k 内做近似平衡切分；
2. **离线码本版**：预先学习若干组“优质 partition 模板”，在线用 PRF 选择模板。

这会让每个位置的单位信息量更高，短文本提升会比较明显。

### 6.7 核心思想七：引入同步头（sync header）与编辑鲁棒恢复

#### 当前问题

前缀链式同步对编辑攻击非常脆弱。

#### 改进方案

在短文本场景，可以把消息分成：

- **同步头**：用于恢复起始对齐和密钥状态；
- **载荷区**：用于承载实际消息；
- **校验尾**：用于一致性验证。

进一步可尝试：

- 使用句级 anchor（例如按句法块或词性模式选择嵌入位点）；
- 用滑窗重同步而不是严格依赖完整前缀；
- 检测时做局部动态规划寻找最优对齐路径。

如果目标论文强调“短文本 + 抗编辑”，这是很好的第二主贡献方向。

### 6.8 核心思想八：从 token 水平上升到 span / semantic unit 水平

对于很短的文本，纯 token 级水印会受字面改写影响过大。可以尝试：

- 只在某些语义等价替换位点写入；
- 利用句法角色（主语、谓语、修饰语）选择相对稳定的嵌入点；
- 将若干 token 组合成一个 span 来承载一个 symbol。

这条路线实现更复杂，但论文新意很强，尤其适合对抗 paraphrase。

## 7. 一个更具体、可落地的新方案蓝图

下面给出一个我认为最可落地、最适合发论文的版本。

## 7.1 方法名建议

**CBE-WM**：Coverage-Balanced Error-corrected Watermarking for Short Texts

### 7.2 编码端

1. **消息编码**：原始消息 `m` 先经过 ECC，得到码字 `c`。
2. **位调度**：不是随机选 bit，而是根据当前覆盖计数选择最少覆盖的码位。
3. **位置选择**：仅在高熵、低风险位置嵌入。
4. **双层 partition**：
   - 主层 partition 承载当前主码位；
   - 辅层 partition 承载校验/同步位。
5. **强度自适应**：根据熵和 margin 调整 `delta_t`。

### 7.3 解码端

1. 重建所有候选嵌入位置；
2. 为每个码位累计软信息 LLR；
3. 使用软输入 ECC 解码；
4. 输出：
   - 水印存在性置信度；
   - 消息恢复结果；
   - 每位 bit 的后验概率；
   - 若失败，给出擦除位位置。

### 7.4 关键理论点

你可以把它写成一个受限信道：

- 信道输入：待写入的码位；
- 信道状态：LM 前缀分布；
- 信道动作：对 logits 做受限偏置；
- 信道输出：采样得到的 token；
- 信道噪声：语言模型随机性 + 文本后编辑。

论文里可分析：

1. 覆盖平衡调度对最小 bit 采样数的提升；
2. 软判决相对硬投票的误码率收益；
3. 熵感知嵌入在固定 perplexity 约束下的容量提升；
4. ECC 在短文本 regime 下的恢复增益。

## 8. 建议的实验设计

要把论文做扎实，实验不能只看 overall hit rate，尤其要单独突出短文本。

### 8.1 长度分桶

按生成长度分桶，例如：

- 16–32 tokens
- 33–64 tokens
- 65–128 tokens
- 129–256 tokens

重点看最短两档。

### 8.2 容量-质量曲线

对每个方法画：

- x 轴：有效 payload（恢复成功的 bit 数）
- y 轴：文本质量（PPL / MAUVE / GPT 评分）

而不是只报单个点。

### 8.3 解码指标

建议至少报告：

- bit error rate (BER)
- block error rate (BLER)
- exact message match
- watermark detection AUC
- average per-bit coverage
- coverage variance
- erasure rate（不确定位比例）

### 8.4 攻击实验

至少包含：

- 截断
- 随机删除 / 插入 / 替换
- DIPPER paraphrase
- 同义改写
- 句序重排（若适用）

### 8.5 消融实验

核心消融建议：

1. 随机 bit 调度 vs 覆盖平衡调度；
2. 硬投票 vs 软 LLR；
3. 无 ECC vs BCH vs Polar；
4. 固定 `delta` vs 熵感知 `delta`；
5. 随机 partition vs 信息量最大化 partition；
6. 单层嵌入 vs 双层嵌入。

## 9. 对当前仓库代码的具体改进建议

如果你准备基于这个仓库继续迭代，我建议代码层面优先做下面几件事。

### 9.1 把“bit 调度器”独立成模块

新增例如 `bit_scheduler.py`：

- `RandomBitScheduler`
- `BalancedBitScheduler`
- `UEPBitScheduler`（unequal error protection）

这样可以清晰做 ablation。

### 9.2 把“partition 设计器”独立成模块

新增例如 `partitioner.py`：

- `StaticRandomPartitioner`
- `BalancedTopKPartitioner`
- `TemplatePartitioner`

便于比较随机 partition 与信息量优化 partition。

### 9.3 检测端改成软输出接口

让检测器返回：

- 每位 bit 的 LLR；
- 每位 bit 的 posterior；
- 是否作为擦除位交给 ECC。

而不只是 `0/1/x`。

### 9.4 加入统一实验配置

当前很多参数散落在脚本里，建议引入：

- YAML/JSON config；
- 固定随机种子；
- 明确保存 commit id、模型版本、tokenizer 版本。

### 9.5 修正实现歧义

至少应先处理：

- 删除重复定义的 `decode_bimark_multibit_watermark`；
- 修正 `verify_bimark_multibit` 的 `weight` 初始化；
- 显式把 prefix 转成 tuple/int list 后再用于 `hist`；
- 去掉逐 token runtime 打印；
- 把私有 token / 设备号改成外部参数。

## 10. 我最推荐的两条论文路线

### 路线 A：最稳妥、最容易发

**主题**：短文本多 bit 水印中的覆盖平衡与软纠错解码

#### 核心贡献

1. 提出 coverage-balanced bit scheduling；
2. 提出 soft LLR decoding；
3. 引入短块长 ECC；
4. 在短文本上显著优于 BiMark 类随机 bit 分配方案。

#### 优点

- 与当前代码最连续；
- 改动难度适中；
- 理论和实验都容易讲清楚。

### 路线 B：创新更强但实现更重

**主题**：面向编辑鲁棒短文本水印的同步头 + 语义单元嵌入

#### 核心贡献

1. 设计可重同步的多 bit watermark；
2. 在 paraphrase / edit attack 下恢复消息；
3. 引入 span-level 或 syntax-aware 嵌入单元。

#### 优点

- 更新颖；
- 更容易和现有 token-level 水印拉开差异。

#### 缺点

- 工程工作量和实验复杂度更高。

## 11. 如果只选 3 个最有价值的改进，我建议是

如果资源有限，我建议优先做下面 3 件事：

### 改进 1：Coverage-balanced bit scheduling

这是短文本多 bit 的第一瓶颈，投入产出比最高。

### 改进 2：Soft decoding + ECC

这是把“可检测”升级成“可恢复”的关键。

### 改进 3：Entropy-aware adaptive embedding

这是保证质量-容量 tradeoff 不崩的关键。

这三者组合起来，已经足够支撑一篇新的论文主线。

## 12. 一句话总结

当前 BiMark 原型的主要问题，不是“不能做多 bit”，而是：

> 它把短文本中最宝贵的少量可嵌入位置，按照“随机 bit 轮询 + 硬投票 + 无纠错”的方式低效使用了。

如果你希望产出一篇新论文，最值得做的方向是把它升级成：

> **面向短文本的、覆盖率受控的、软解码的、带纠错编码的自适应多 bit 水印系统。**

这个方向既与现有代码有连续性，又能形成明确的方法创新、理论分析和实验优势，尤其适合把“短文本里嵌入多 bit 信息”作为论文主卖点。
